# frotzsmith — Security

**Document 06 of 13 · Security**

frotzsmith is a static, client-only app: no accounts, no database, and the author's source and story files never leave the browser except via explicit downloads the author initiates. That eliminates whole categories of risk (no DB, no auth surface) but introduces a few specific to running a compiler and untrusted story files in-browser.

**One thing runs on a server** (since 0.2.5): the report function (`netlify/functions/report.mjs`), which emails what a person writes in *Report a problem* / *Suggest a feature* to the maintainer. It is the only remote surface and the only place a secret lives; §10 covers it.

---

## 1. Threat model (honest and bounded)

| Asset | Threat | Mitigation |
|-------|--------|-----------|
| The author's source | Loss | localStorage autosave + explicit project export (Doc 05). |
| The browser tab | A malicious/buggy story file or pasted source hanging or abusing the page | WASM/interpreter sandboxing; Web Worker isolation for replay; teardown discipline. |
| The DOM | XSS via rendered game output or error text | Treat all interpreter output and compiler stderr as untrusted text; no `innerHTML` of unsanitized content. |
| Exported bundle recipients | A shared `.html` doing something unexpected | Bundle contains only pinned runtime + the author's story; no remote requests; self-contained. |
| Imported projects | Malicious project JSON | Strict validation, text-only treatment, never `eval`. |
| The maintainer's inbox and email quota | A script posting to the report function | Same-site JSON posts only, a per-address limit at Netlify's edge, a daily cap, fixed recipient, size limits (§10). |
| The IDE's origin | A hostile game source (package, share link) compiled and run by the IDE's own interpreters, which share the IDE's origin | ZVM's JIT injection patched (§3); outside sources don't auto-run (§6.1); CSP (§9). |

The only remote attacker surface is the report function (§10); it holds no user data and cannot reach the IDE. In the browser, the realistic risks are **self-inflicted** (a runaway game freezing the tab), **XSS via untrusted text** (game output, error messages, pasted source), and **a hostile story reaching the interpreters**: a package or share link delivers *source*, the author compiles it, and the compiled story runs in interpreters that share the IDE's origin (the Play iframe is `allow-same-origin allow-scripts`; the replay worker is same-origin). The play page's blob: gate (§3) stops *other people's* story files, not a story the author compiles.

## 2. WASM compiler sandboxing

- The `inform6` WASM module runs in the browser's WASM sandbox: no filesystem beyond MEMFS, no network. It cannot touch the host.
- **Single-threaded build** (no pthreads / `SharedArrayBuffer`) — chosen also to avoid needing COOP/COEP cross-origin-isolation headers, keeping the site "deploy anywhere static."
- **A fresh module instance is created per compile** (the I6 compiler isn't safe to run `main()` twice — Doc 01 §2.2), so each run starts from clean memory and a fresh MEMFS; no stale artifacts leak between runs.
- **Compile runs in a Web Worker** so a pathological source that makes the compiler spin doesn't freeze the UI, and a main-thread wall-clock timeout can `terminate()` it and report "Compile timed out." This is required, not optional: a synchronous compile on the main thread cannot be aborted (the timer can't fire until it returns).

## 3. Interpreter / story-file sandboxing

- Story files are untrusted by definition (the author may paste/import someone else's `.inf`, or compile experimental code).
- Interpreters run in the browser sandbox and cannot escape to the host. Two copies of the pure-JS Z-machine **ZVM** ship: the vendored Parchment build (`public/play/web/zvm.js`, the Play tab) and ifvms 1.1.6 from npm (bundled into the headless replay worker). Glulx is not played in the browser (Quixe is not vendored).
- **The Play tab's default player is frotzplay** (`@frotzinc/player` on `@frotzinc/zmachine`, since 0.2.0), mounted in the IDE's own page, not a frame. Its interpreter decodes and runs one instruction at a time: no `eval`, no `new Function`, no generated code, so a story cannot make it execute JavaScript the way a JIT can. It runs in slices on the main thread and yields between them, so a looping story does not freeze the tab. Its output is rendered by Vue as text. Its autosave is off in the IDE (`:autosave="false"`). Parchment remains as a choice, and ZVM (ifvms) still runs every headless replay; the points below are about those two.
- **They are not an origin boundary.** The Play iframe needs `allow-same-origin allow-scripts` (the IDE reads its DOM and feeds Send to Play), so code running in it can reach the IDE's DOM and storage; the replay worker is same-origin too. Anything a story can make the interpreter *execute* is therefore same-origin script. Long term, an opaque-origin sandbox for both (talking over `postMessage`) would close this class; it is not built yet.
- **ZVM JIT injection, patched (audit 2026-11-04, F2).** ZVM compiles any string that uses an abbreviation into `Function('return"…"')`, using U+E000 as the placeholder around `+this.abbr(N)+`, after escaping only `\`, `"` and `\r`. A story whose Unicode table maps a character to U+E000 (Inform 6: `Zcharacter table + '@{E000}';`) put a bare `"` into that source and ran arbitrary JavaScript — proven with a story compiled by our own inform6.wasm, in both copies. Both copies now map a Unicode-table entry of U+E000 or a C0 control other than 13 to U+FFFD, and also escape `\n`, U+2028 and U+2029. The vendored file is patched in place (header comment; `public/play/web/README.md`); ifvms is patched at build time by `tools/ifvms-text-fix.mjs`, which **fails the build** if either line changes in an upgrade, or if a bundle holds modules under `ifvms/src/zvm/` but `ifvms/src/zvm/text.js` never went through the patch. (If an upgrade moved ifvms's sources elsewhere, e.g. to `dist/`, neither check would match; the built-worker smoke test below is the backstop that fails then.) The same plugins run in the `nuxt dev` pre-bundle (`optimizeDeps.rolldownOptions.plugins`), which otherwise skips them, so the dev replay worker is patched too. `app/modules/inform6/engine/zvm-text-jit.test.ts` runs the PoC against unpatched ifvms and the vendored copy with its two edits undone (must fire), patched ifvms and the vendored copy (must not); `tools/smoke-replay-worker.mjs` replays the PoC fixture in the **built** worker after every `generate`.
- **The Play page's story gate:** `public/play/index.html` accepts `?story=` only as a blob URL minted by this origin (`blob:<origin>/…`, the IDE's own compiled output) and otherwise plays the bundled demo, so a crafted link can't hand the player someone else's story file (`tools/play-page.test.ts`).
- **Messages from the Play iframe** are accepted only from our origin, from that iframe's own window (`e.source`), and tagged by our play page (`app/utils/play-message.ts`); their values are text, never executed.
- **Headless replay runs in a Web Worker** (one fresh worker per run, terminated afterwards), so an infinite game loop or huge output doesn't lock the main thread. Each run has a wall-clock budget of 15 s + 250 ms per command, capped at 2 minutes (`replayBudgetMs`); overruns terminate the worker and are reported cleanly. There is no separate turn cap — a run executes exactly the script's commands.
- Output volume is bounded: each turn's captured text is capped at 256 KB with a visible "output truncated" notice (`MAX_TURN_OUTPUT_CHARS` in `headless-glkote.ts`), so a game that prints forever can't grow the worker's memory until the timeout.

## 4. XSS / output handling

All three text streams are **untrusted** and must never be injected as HTML:
1. **Compiler stderr** (error/warning messages) — rendered as text content, not HTML.
2. **Game output** in the Play tab — frotzplay renders it as text through Vue (no `v-html`); with Parchment chosen, Parchment/GlkOte handles rendering in its frame. frotzsmith doesn't post-process it into the DOM as raw HTML.
3. **Game output** in the Transcript tab — rendered as text content; if any styling is applied, it's via safe DOM construction, never `innerHTML` of game text.

Where frotzsmith itself renders any of this (Transcript, Results), it uses text nodes / framework text binding (Vue's default escaping), never `v-html` on untrusted content. (The markdown editor already established DOMPurify discipline for *its* HTML rendering; frotzsmith's surfaces are plain text, so the rule is simply "no raw HTML from untrusted sources.")

## 5. Export hygiene

- **Filenames** for downloads come from `slugify` (`app/utils/slug.ts`): the story title is reduced to lowercase ASCII letters, digits and hyphens, so a title can't carry a path, a separator or an invalid character.
- **Playable bundle (frotzplay, the default)**: one HTML file from `@frotzinc/player`'s `bundle()` — the `<frotz-play>` script, the story as base64 in a data block, and its own `Content-Security-Policy` (`default-src 'none'`, the two scripts and the style allowed by hash). The title is HTML-escaped. *Export folder (.zip)* holds the same pieces as files; its folder name is the slug.
- **Playable bundle (Parchment)**: assembled from pinned local runtime + the author's story bytes only. No remote `<script src>`, no fetches → the artifact can't be a vector for pulling in remote code, and works offline.
- **Project export JSON**: plain data; no executable content.

## 6. Import validation

- Project import: parse JSON in a try/catch, validate required fields and types against the `ProjectExport` shape, reject unknown shapes with a clear message, treat `source`/`scripts` strictly as text. Never `eval`, never construct functions from imported strings.

### 6.1 Project packages (`.frotzsmith`)

A `.frotzsmith` file is untrusted input, read entirely in the browser.

- **Limits, checked before inflating:** archive <= 32 MiB; <= 2,000 entries; each entry <= 8 MiB and total <= 32 MiB uncompressed; compression ratio per entry <= 200:1. Sizes declared in the headers are verified against the actual bytes; CRC mismatches are refused.
- **Container rules:** first entry `mimetype` (stored, exact content); exactly one end-of-central-directory record, with **no archive comment** (another unzipper could find a second archive in it); entries stored or deflated only, and a deflate stream must end exactly where the entry's data does; extra fields must be well-formed and must not carry an Info-ZIP Unicode Comment field (`0x6375`) or a Unicode Path field (`0x7075`) naming anything but the entry itself (a second name other tools show); a Unicode Path field that only repeats the name — version 1, matching CRC, byte-equal UTF-8 name, as Info-ZIP on Linux writes for non-ASCII names — is allowed. Unix file-type bits are checked **from any "made by" host**: symlinks, FIFOs and devices are refused, and so is a file that is also another entry's folder (`a` next to `a/b`). The manifest is <= 1 MiB JSON.
- **Path rules** (`app/project-package/paths.ts`, shared by reader, manifest and writer): UTF-8 `/`-separated paths with no `..`, `.`, empty segments, leading `/`, backslash, drive letters, control characters, DEL or lone surrogates; nothing Windows or macOS can't hold — `: < > | ? * "`, a trailing dot or space or a leading space in any segment, a Windows device name in any segment with any extension (`CON`, `nul.txt`, `COM0`–`COM9`, `COM¹²³`, `LPT` likewise, `CONIN$`, `CONOUT$`); no invisible or deceptive characters (Unicode Cf — bidi controls, zero-width characters, BOM, soft hyphen, tags —, Zl, Zp, private use, the Hangul fillers, and the slash/backslash look-alikes U+2044 U+2215 U+29F5 U+29F8 U+FF0F U+FF3C). Two paths collide when equal after NFKC + a full case fold (upper- then lower-casing, twice: `ẞ`/`ß`/`ss`, `ſ`/`s`, `ı`/`i`, `ﬀ`/`ff`). A download always reopens because the writer never writes a path the reader refuses: names it makes up get `_` after a Windows device name (`tests/con_.txt`, `aux_.inf`, `nul_.h`), and files kept from before these rules (hidden files with now-refused or colliding names, uploads named like a library file, or two uploads that would mount under one Include name) are left out of the download — kept in the browser, never deleted — and the download toast names them. An upload saved under a new name (`aux.h` → `aux_.h`) is named too, since its Include line changes on reopening. The writer still refuses, with one sentence, what it can't leave out (a NUL in text, over the size or test-script limits).
- **Library files can't be replaced:** an include whose Include name or file name matches a library file of any profile (Standard Library or PunyInform), ignoring case, refuses the whole package. A manual upload with such a name is refused. (The code can record an explicit override on an extension, but the UI doesn't offer one yet — it is planned with the desktop package work; until then the refusal is outright.) The compile writes extensions first and the library after them, so without that recorded choice the library always wins. A library-named upload stored before this rule is kept but no longer mounted at all; on the next load the author is told once, in plain English, that it no longer replaces the library, and it is left out of downloads.
- **Extensions are named before they land:** a package that installs or enables any extension always asks first, naming each one (extensions are shared by every Inform 6 game in the browser); the "Project opened" toast names them too.
- **ZIL includes are per project, never per language.** A ZIL package's other `.zil` files open as that project's own files (shown in the explorer, compiled only when an `INSERT-FILE` line names them); they don't reach any other ZIL game, so unlike extensions they don't force the open dialog — but the dialog, when it shows, and the "Project opened" toast name them (display-safe, at most 5 + "and N more"), and opening over a project with other extra files names those as replaced. They are capped at 100 files, 1 MiB each and 4 MiB in all, with the same path rules, and must not collide with the main file or each other; a package over any of these is refused whole with one sentence and nothing changes (the writer checks the same set, and a download leaves out — and names — a file it can't hold, such as one colliding with the main file's name, or a hidden `.zil` kept by an older version that isn't text, so it always reopens). Project files are searched before the ZIL library, so a project's own file named like a zillib file (e.g. `parser.zil`) shadows the library — for that project only, never for other games. A warning for that clash arrives with M2c. A share link carries only the main file; the "Share link copied" toast says so when the project has other files.
- **Hidden files are named:** files kept with a project that the IDE doesn't show are listed by name (display-safe, at most 5 + "and N more") in the open dialog, the opened toast and the download toast.
- **Names are shown safely:** every name or title quoted in a message goes through `displayPath` — controls, format, separator, private-use and unassigned characters and the Hangul fillers become U+FFFD, combining marks are capped at 2 per character, names are cut to 60 characters + "…" — and is quoted (“…”), so a file name can't pose as part of the sentence.
- **Test scripts are capped:** at most 200 per package and 1 MiB of script text in all (they live in localStorage); beyond either the package is refused, and the writer refuses the same. Test-script buckets are a prototype-free map, so a game titled "Constructor" works.
- **A solution is text only and never runs.** A package may carry the game's solution (`solution.txt`, named by the manifest's `solution` field). The reader accepts it only as UTF-8 text without NUL, at most 1 MiB, and it must fit the browser's 2 MiB solutions store beside the other games' (checked before the first write); otherwise the whole package is refused with one sentence and nothing changes. The writer refuses the same, and steps the name around a hidden file or folder already called `solution.txt`, so a download always reopens. Opening never plays, replays or feeds its `> ` commands anywhere: they reach Play or the headless replay only when the author presses Record or Continue recording, explicit clicks that boot Play and so, like Play, mark the source trusted. Regenerate is refused while the source is untrusted, so it can't replay anything until the author has pressed Play, Run, Record or Continue recording. Opening replaces the game's solution (none clears it), so a different solution already saved for that game is named as replaced in the open dialog, and the dialog says "It includes a solution." The opened solution stays behind the spoiler guard until the author presses Show solution; it is shown as plain text (`textarea` / text nodes), never as markup.
- **Source only:** everything read is treated as text. Compiled stories (`.z3 .z4 .z5 .z8 .ulx .blb .zblorb`) are ignored, never written.
- **Nothing runs on open:** opening loads text into the editor, extensions, test scripts, Skein and solution. It does not compile, play, replay or run the Skein, and no imported string is evaluated.
- **…and nothing runs on the first Compile either.** The Skein's *Auto-run on compile* (on by default) would replay the opened game in the headless interpreter on Compile, with no Play click. A source that came from outside — a package, a share link, or a plain `.inf`/`.zil` file opened with Open — is marked (`app/composables/outside-source.ts`; `frotzsmith:<lang>:outside-source` in localStorage, so it lasts as long as the autosaved source it describes, per language), and auto-run waits while the mark is set; the Skein panel says so in one line (that note is per language too). Only the author's Play or Skein Run in that language clears it, or replacing the source with their own (a bundled sample, New). Editing doesn't.
- **Refusal is whole:** any violation (wrong language, over the uploaded-extension budget, a bad path, a manifest nested deeper than 64 levels, a plain `.zip`) refuses the entire package with one sentence; every check runs before the first write, so a refused package changes nothing. Once accepted, the open is applied in full in the IDE; if browser storage refuses a write (quota), the open still completes in memory and the storage-full notice says the work isn't safely saved. Opening over existing work — edited source, different uploaded extensions, or test scripts / a Skein / a solution already saved for the game the package opens as — asks first, and the dialog names what would be replaced.
- **A Skein is rebuilt, never trusted:** every tree that is loaded — from a package, a `.skein` import, or an IndexedDB restore — goes through `sanitizeTree`, which rebuilds it into fresh objects holding only the known node fields (so a `__v_isRef`/`value` pair can't make Vue show and replay another command, and deep junk can't break saving or download) and refuses node ids outside `^[A-Za-z0-9_-]{1,64}$` or starting `__` (Vue's `__v_*` keys, `__proto__`). The live tree is held `markRaw`, not as a deep reactive proxy. A `.skein` document nested more than 64 levels deep is refused. A `.skein` import is capped at 8 MiB and asks before replacing a Skein that has nodes; opening a plain source file asks before replacing edited source.
- **A Skein that can't be opened is kept, not refused:** a Skein that doesn't parse, is nested too deeply, has a bad node id, isn't a single tree (cyclic, orphaned), or is over 10,000 nodes / 10,000 levels deep is not loaded; it is kept byte-for-byte as a hidden file, written back on the next download, and the user is told "The project's Skein couldn't be opened".

## 7. localStorage hygiene

- frotzsmith's own keys are namespaced (`frotzsmith:*`, per language as `frotzsmith:<lang>:*`) to avoid collisions. **Exception:** the vendored Parchment player writes its own `autosave:<story-hash>` keys (same origin); the IDE removes them when a new source loads, on every compile and before Send to Play (`clearPlayAutosave`), so a game restarts from the beginning.
- Quota-exceeded handled gracefully (warn, continue in memory) — the markdown editor's pattern.
- No secrets are ever stored (there are none — no auth).

## 8. Dependency pinning

- `inform6.wasm`, the standard library, PunyInform, and the Parchment runtime are **pinned** in-repo (the swappable-bundle model lets them be updated deliberately, with review, not silently). This is both a reproducibility and a supply-chain measure.
- **Vendored files have recorded provenance** (audit 2026-11-04, F16): `tools/vendored-files.json` lists each served third-party file (Parchment's `public/play/web/*`, jQuery 3.5.1, the Plausible tracker `public/pa/script.js`) with its source and the sha256 of the committed bytes; `tools/vendored-files.test.ts` fails on any unrecorded change, and also undoes our local patches to check the upstream hashes. The exact Parchment release wasn't recorded when it was vendored; jQuery is byte-identical to the official 3.5.1 file (less a trailing newline).
- npm dependencies install from `yarn.lock` with `--frozen-lockfile`, in CI and on Netlify. On Netlify that takes two settings in `netlify.toml`: `YARN_FLAGS = "--frozen-lockfile"` freezes Netlify's own automatic install, which runs before the build command and would otherwise rewrite a drifted lockfile so that the build command's frozen install passes; the build command's install is a second check. CI's GitHub Actions are pinned by full commit SHA (tag in a comment; Dependabot updates them), and the one `npx -y` tool is pinned to a version (`tools/supply-chain.test.ts`).
- **Analytics** are first-party: the Plausible tracker is the vendored file above (not a live proxy of plausible.io's script — audit F5), and only the event beacon `/pa/event` is proxied (`public/_redirects`). The desktop build loads no analytics.

## 9. Content Security Policy (deployment)

`netlify.toml` sends this policy for every path; `tools/netlify-headers.test.ts` pins it exactly, along with `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a `Permissions-Policy` that turns off camera, microphone, geolocation and payment, `Strict-Transport-Security: max-age=31536000; includeSubDomains` (stated so the custom domain sends `includeSubDomains` too; no `preload`, which is a decision for all of frotzinc.com) and `Cross-Origin-Opener-Policy: same-origin`.

```
default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval' 'wasm-unsafe-eval';
style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:;
connect-src 'self' blob:; worker-src 'self'; frame-src 'self'; child-src 'self';
frame-ancestors 'self'; base-uri 'self'; form-action 'self'; object-src 'none'
```

It is honest to say this is **loose**: script-src allows inline script and eval site-wide. Why each relaxation is there:

| Source | Why it is needed |
|---|---|
| `script-src 'unsafe-eval'` | ZVM is a JIT: it compiles z-code routines and abbreviated strings to JavaScript with `new Function` (both copies, §3). The replay worker also runs the sloppy-mode `glkapi.js` through indirect `eval`. This is what makes the F2 injection (§3) dangerous, and why ZVM's code generation is patched rather than trusted. |
| `script-src 'wasm-unsafe-eval'` | `inform6.wasm` and the .NET ZILF runtime are instantiated from bytes. |
| `script-src 'unsafe-inline'` | The Play page (`public/play/index.html`) has inline scripts (the story gate, the command/room reporters) and Nuxt's static SPA output has an inline bootstrap. Moving them to files or hashes is possible future work. |
| `style-src 'unsafe-inline'` | Nuxt UI / Vue style bindings and GlkOte's inline styles. |
| `img-src data:`, `font-src data:` | Inlined icons and fonts. |
| `connect-src blob:` | Parchment `fetch()`es the compiled story from the blob URL the IDE hands it. |
| `frame-ancestors 'self'` / `frame-src 'self'` | The IDE frames its own Play page; nobody else may frame the IDE. |

**No third-party origin appears anywhere** (analytics is first-party, §8). **`blob:` was removed** from `script-src`, `worker-src`, `frame-src` and `child-src` (audit 2026-11-04, F11): every worker is a same-origin module file, the Play iframe loads `/play/index.html`, and blob URLs are only fetched (the story) or used as `<a download>` targets. This was checked in Chrome under the tightened policy with a `report-uri`: an Inform 6 compile, Play, a headless replay, a ZIL compile and Play raised no violation (a test blob worker was blocked and reported).

### 9.1 Service worker (offline website)

The website registers a Workbox service worker (`@vite-pwa/nuxt`, configured under `pwa` in `nuxt.config.ts`) so it works offline after the first visit. Its scope is deliberately small:

- **Precache: the app's own files only** — the pages, the `_nuxt/` chunks and workers (the Inform 6 compiler's wasm among them), the Parchment player under `play/`, the demo story, fonts and icons. Explicitly excluded: `zilf/**`, `pa/**`, `og-image.*`, `200.html`, `404.html`. Precached entries are revisioned by Workbox; outdated caches are cleaned up on activation.
- **One runtime cache: `frotzsmith-zilf`.** Requests whose **pathname** is `/zilf/r<rev>/_framework/*` (the route matches the path only, whatever the origin — harmless, because the app makes no cross-origin requests and an opaque cross-origin response has status 0, never the 200 the route requires) (the ZILF .NET runtime, ~13 MB) are served **CacheFirst** and stored only on a **200** response — never a 404, an error or an opaque response, so a bad fetch can't poison the compiler for good. The path carries the ZILF revision, so CacheFirst can't serve a stale runtime after an upgrade. Nothing is downloaded until ZIL is used.
- **Never cached:** `/pa/` (the vendored Plausible tracker and the event proxy — pageviews stay live and offline visits simply aren't counted) and **any third-party response** — the app makes no cross-origin requests (CSP `connect-src 'self' blob:`, §9), and the one runtime route keeps only status 200, which an opaque cross-origin response never has.
- **Updates never apply without the author.** `registerType: 'prompt'`, `skipWaiting: false`: a new worker installs and waits. The page offers *"A new version of frotzsmith is ready"* (**Reload** / **Later**); only the author's **Reload** tells the waiting worker to take over, and only that tab reloads, after its pending saves are written. Other tabs keep their offer. `sw.js` and `manifest.webmanifest` are served `no-cache` (`netlify.toml`), so a deploy is noticed, not stuck behind an HTTP cache.
- **Nuxt's own reloads are off.** Nuxt 4 by default polls `builds/latest.json` hourly and reloads the page on the next in-app navigation once a new build exists, and reloads on a chunk that fails to load — both without writing the pending saves. `nuxt.config.ts` sets `experimental.checkOutdatedBuildInterval: false` and `experimental.emitRouteChunkError: 'manual'`; a chunk error shows the update offer instead (`plugins/service-worker.client.ts`, `app:chunkError`). A long-lived tab still learns of a deploy: the plugin calls `registration.update()` hourly, which can only raise the offer.
- `tools/check-sw.mjs` (run by `postgenerate`) reads the built `sw.js` and fails the build if any excluded path is precached, the `/` app shell is missing, or the ZILF runtime route is missing or not a pathname-matched, 200-only `CacheFirst`.
- **Kill switch (removing the worker).** To remove the service worker from every visitor, deploy a build made with **`FROTZSMITH_SW_KILL=1`** (e.g. as a Netlify build environment variable, then trigger a deploy). That sets `pwa.selfDestroying: true`: the deployed `sw.js` installs at once, unregisters itself, deletes every cache frotzsmith made, and reloads its open pages from the network. `check-sw` checks that shape in that mode. **A rollback alone does not remove the worker:** rolling back to a deploy from before the service worker makes `/sw.js` a 404, and an installed worker that gets a 404 on update simply stays, serving its precache indefinitely. So: deploy the kill build first, leave it up long enough for visitors to come back (open tabs pick it up within the hourly check), then roll back or redeploy normally. This is the **one path that reloads pages without the author pressing Reload**, by design; it does not wait for an open tab's pending (debounced) saves, so the last second of typing can be lost; work already saved in the browser's storage is untouched (only Cache Storage is cleared).
- The desktop build (`FROTZSMITH_DESKTOP=1`) ships no service worker, no manifest and no registration code.

## 10. The report function (the one server-side piece)

*Report a problem* and *Suggest a feature* (the About menu) can send what the person wrote by email. The browser posts to `/.netlify/functions/report` on its own site (so `connect-src 'self'` covers it); the function sends it to the maintainer through Resend. The handler is `@frotzinc/nuxt-base`'s; frotzsmith puts a guard in front of it (`netlify/lib/report-guard.mjs`, tested by `tools/report-guard.test.ts`).

- **What leaves the browser, and only on Send:** the text the person typed, the reply address if they gave one, and, if the box is ticked, the technical details shown in the form (the app's version and build, and the browser). Never the source or a story file. Netlify sees the sender's IP address, as for any request; the function uses it only to count requests and does not put it in the email or store it.
- **The secret:** `RESEND_API_KEY` is a Netlify environment variable, read by the function and never sent to the browser. `REPORT_TO` and `REPORT_FROM` are environment variables too: the recipient is fixed, never taken from the form, so the function cannot be used to mail anyone else. Without them it answers 503 and the dialog offers GitHub.
- **Text only:** the email is plain text. Every field is cut to a limit, control characters are removed, the body is at most 32 KiB, and the title is made one line before it becomes the subject. The reply address must look like one address (no spaces, commas or angle brackets).
- **Against a flood** (review 2026-11-09 — what the handler alone relies on is either sent by the client, `elapsed` and the hidden field, or kept in one instance's memory):
  - *Same site only.* The `Origin` header must name the host the request came to, and the body must be `application/json`. A page on another site cannot post from a visitor's browser.
  - *Per address.* Netlify's rate limiting (`config.rateLimit` in the function file): 5 posts a minute per IP address, refused with 429 at the edge before the function runs.
  - *Per day.* At most 100 reports are sent a day, counted in Netlify Blobs (`report-count`, one small number per day). Past that the function answers 429 and the dialog offers GitHub. A script that forges its headers and rotates addresses stops here. If the counter cannot be read, the report still goes.
- **The desktop build** has no report endpoint; it offers GitHub only.

## 11. Summary

The client-only architecture is the biggest security win — the one remote surface is a small function that only sends mail to a fixed address (§10). The real work is (a) sandboxing/timeouts so untrusted source and story files can't hang or exhaust the tab, (b) treating all compiler and game text as untrusted plain text in the DOM, and (c) remembering that the interpreters share the IDE's origin, so their code generation must not be steerable by a story (§3) and outside sources must not run without the author's click (§6.1).
