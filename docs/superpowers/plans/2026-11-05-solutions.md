# Solutions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Solution tab in the right pane shows a full retelling of the game (opening text, every command, every reply).
- For samples it is generated from a bundled walkthrough.
- For any game the author can record one from Play (green light = recording, red = stopped).
- The solution is a `solution.txt` the author can edit in the left pane, regenerate, download, and carry in `.frotzsmith` packages.

**Architecture:**
- Solution text is always produced by replaying commands headlessly from the start of the game, through the existing replay worker (`useReplay` / `useTranscript`).
- A pure module holds the text format.
- A per-game store, keyed like test scripts, holds each game's solution.
- A generator composable replays commands into text.
- The tab, the explorer entry and the package fields sit on top.

**Tech Stack:** Nuxt 4 SPA, Vue 3.5, Nuxt UI 4, TypeScript, vitest (happy-dom + `.nuxt.test.ts` harness), Inform 6 WASM and ZILF .NET WASM compilers, ifvms ZVM replay worker.

**Spec:** `docs/superpowers/specs/2026-11-05-solutions-design.md`

## Global Constraints

- **Node:** shell prefix `export PATH="$HOME/.nvm/versions/node/v22.23.4/bin:$PATH";` (Nuxt needs Node ≥ 22.22.3).
- **Text format:**
  - Command lines are exactly `> <command>` at line start. Everything else is game text.
  - The header is the first line `<title> — solution`, then `(generated by Frotzsmith from N commands)`, then a blank line, then the opening text.
- **Storage:**
  - The store lives in localStorage at `frotzsmith:<lang>:solutions` → `{ v: 1, buckets: { [storyKey]: { text: string } } }`.
  - The buckets are null-prototype and read with `Object.hasOwn`.
  - Writes go through `safeSetItem` + `notifyStorageFull` and never throw.
- **Caps:** 1 MiB per solution and 4 MiB for the store, by UTF-16 length. A refusal is one plain sentence.
- **Spoiler guard:** the solution text is never shown until the author presses **Show solution**.
- **No silent replacement:** nothing replaces an existing solution without asking. That covers Record over an existing solution, Make it my solution, and opening a package that carries one.
- **Recording restarts Play from the beginning.**
- **Package:** `solution.txt` at the root, manifest `"solution": "solution.txt"`. The reader accepts it only as UTF-8 text of at most 1 MiB; otherwise it refuses the whole package, as the reader already does for bad entries.
- **User-facing text:** plain English, one sentence, names through `displayPath`/`quotedPath`.
- **Commits:** conventional; NEVER a Co-Authored-By or any AI trailer. Do not push.
- **Gates per task:** `yarn test`, `yarn typecheck` (0 errors). Tasks 3 and 5 also run `npx nuxt generate` + `node tools/inject-preloads.mjs && node tools/smoke-replay-worker.mjs && node tools/check-sw.mjs`.

## Review Focus

1. **Huge solutions:** a 60-command game's full text stays under the cap; a solution over 1 MiB is refused, never truncated silently. *Task 1.*
2. **Recording interrupted:** a recompile, a game switch or a reload stops recording; nothing half-saved is written, and the author is told. *Task 4.*
3. **Editing then Regenerate:** removing a `> ` line and regenerating gives text without that command's reply; free text the author added between commands is replaced, and the author is warned in the confirm. *Tasks 2 and 4.*
4. **Engine errors or games that end early:** replay stops at the game's end or at an error; the text so far is kept, with a one-line note. *Task 2.*
5. **Sample loaded, then edited or replaced:** the sample solution still shows for an edited sample (with the note), and disappears after New, Open, a package or a share link. *Task 2.*

**Interfaces (produces):**
- `formatSolution(title: string, opening: string, turns: { command: string; output: string }[]): string`

- `planSolution(text: string, otherTotal: number): { ok: true } | { ok: false; message: string }`, which enforces both caps.
- `useSolutions()` returns:
  - `text: ComputedRef<string | null>`, the active game's solution;
  - `set(text): { ok: true } | { ok: false; message }`;
  - `edit(text)` (debounced persist, memory at once; same pattern as `useZilProjectFiles.edit`);
  - `clear()`;
  - `has: ComputedRef<boolean>`.
  - The active game is the story key that `useIde`'s `activeStoryKey` already uses.

  - The store keeps one solution per story key, survives a reload, and is prototype-free (a game titled "constructor" works).

### Task 4: The Solution tab, recording (record / pause / resume / stop / continue), load, copy, regenerate, download, clear

> **Revised 2026-11-05 (author's follow-up):**
> - **States and lights:** three states, Recording (green), Paused (amber) and Stopped (red), each shown as a dot plus a word.
> - **Controls:**
>   - **Record** starts from scratch and asks before replacing.
>   - **Pause** saves the captured commands as the solution (via `generate`), then stops capture so the author can edit.
>   - **Resume** and **Continue recording** both restart Play, feed it every `solutionCommands(currentText)` via `useIde().sendToPlay`, switch to the Play tab first, then capture and append.
>   - **Stop** is "save": it saves the same way Pause does and ends the session.
>   - **Load file…** opens a `.txt` (≤ 1 MiB), asks before replacing, and Continue can carry on from its end.
>   - **Copy** puts the text on the clipboard.
> - **Automatic changes:** a recompile pauses the session, a game switch stops it, and a reload ends it with a notice.
> - **Recorder interface:** `{ state: Ref<'recording' | 'paused' | 'stopped'>; record(); pause(); resume(); stop(); continueRecording() }`, where each returns a result `{ ok } | { ok: false; message }`.
> - **Tests:**
>   - Pause, then edit (delete a `> ` line), then Resume feeds the edited command list to `sendToPlay` and appends new captures after it.
>   - Load a partial file, then Continue, then type two commands, then Stop gives a solution with the file's commands plus the two.
>   - A recompile while recording pauses the session.
>   - Copy writes the text to the clipboard (stub `navigator.clipboard`).
>
> - **Layout (author, 2026-11-05):** when a session starts, the right pane shows Play and the left pane opens `solution.txt`.
>   - While Recording, the left-pane solution is read-only and regenerates live: debounced about 300 ms, after each captured command, scrolled to the end.
>   - While Paused or Stopped, it is editable.
>   - The light plus Pause/Resume and Stop sit at the top of that left-pane tab.
>   - This needs Task 5's `solution` explorer tab id. Task 4 adds the live-regenerate and the read-only flag through `useSolutions`, and Task 5 renders the left-pane header controls. Note this in Task 5's dispatch.
>
> Where this note conflicts with the text below, this note wins.

Panel behaviour, per the spec:

- **Sample section:** shown when `loadedSampleId` is set; carries the edited note when `sampleEdited`; **Make it my solution** asks before replacing.

  - **Download** writes `<storyBase>-solution.txt`.
